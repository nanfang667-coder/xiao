# 团队固定发帖额度

团队发帖额度按账号累计使用，不按月份自动重置或发放。总额度 150 条、累计使用 100 条时，跨月仍剩 50 条；管理员追加 20 条后剩 70 条。

## 计算规则

- 总额度为账号当前基础额度加数据库中保留的追加额度。
- 已用额度为该账号全部历史 `kind=create` 且状态为 `pending` 或 `approved` 的提交数，包含普通发帖及分配稿提交。
- 拒审释放额度；分配稿重提复用原记录，重新占用一次额度；修改类提交不占用新帖额度。
- 普通删帖仍保留已通过的提交记录，不会退还已消耗额度。
- 管理员增加额度采用原子累加，不再因月份变化覆盖之前的追加值。现有单次增加 1–1000 条、累计追加最多 10000 条的限制保留。

## 月初已归零的账号

旧代码只按当前月份筛选提交记录，没有在月初删除记录或将使用次数写为零。因此部署新代码后，仍保留的历史提交会自动重新计入，通常无需恢复数据库或批量修改记录。月初至部署前新增的待审核/已通过帖子也会计入；如果累计使用已超过总额度，剩余显示为 0，直到额度足够。

额度计算沿用 `monthlyPostLimit`、`monthlyPostLimitOverride`、`monthlyPostBonus` 字段以兼容既有数据；`monthlyPostBonusMonth` 仅保留旧信息，不参与额度计算。固定额度计算本身不需要迁移；下述额度记录功能需要新增独立流水表。

若旧代码已在新月份追加过额度，之前月份的追加数可能已经被覆盖。启用记录功能之前没有额度变更流水，无法从当前字段准确推算被覆盖的值，需要管理员依据已确认的历史数额补加。删除账号造成的提交记录删除也无法由本次计算修复。不要因月初显示归零而重新导入帖子，以免产生重复记录。

## 额度变更记录

在“团队账号管理”点击“额度记录”，可按账号和北京时间月份筛选。每个账号旁也有单独入口。新建账号、追加额度和调整基础额度都会保存账号名称、变更值、变更前后总额度、实际操作时间；保存相同基础额度不产生重复记录。记录仅管理员可查看，删除团队账号后仍保留历史账号名称和记录。

额度写入与操作记录使用同一事务。记录写入失败时，额度修改也回滚；未完成记录表升级时，新增账号和额度修改暂不允许执行，以免产生没有记录的变更。现有账号登录、发帖与查看不受记录表是否启用影响。

启用时对每个现有账号保存一次“旧数据快照”：当前总额度、当前保留的追加数和旧月份标记。快照采集时间是启用时间，历史追加的具体时间未知；快照中的追加数不代表该月份新增条数。例如筛选 `2026-09`，会包含旧月份标记为九月的快照，但不会伪造九月的逐次操作。若月份标记已经被旧代码覆盖，就无法仅凭现有字段还原九月的信息。启用后每一次成功变更才有完整、准确的操作记录。

新增迁移为 `prisma/migrations/20261001000100_add_team_post_quota_events/migration.sql`。本地或部署环境启用时，生成匹配的 Prisma Client，并运行 `node scripts/apply-team-quota-history-schema.mjs --apply` 后重启服务。该定向脚本仅应用本次新表、索引和一次性快照，不运行其他待处理迁移、不改账号额度、不删除帖子；重复执行不会重复生成快照。脚本读取该环境的配置以定位数据库，不向终端输出账号、额度或环境值。

## 验证与上线核对

自动化测试使用虚构账号和内存数据，覆盖跨月/跨年余额不变、历史使用重新计入、拒审和重提、额度耗尽拦截、幂等重试、并发追加及前后台显示一致。流水测试额外覆盖新增/调整/追加的事务记录、日志写入失败回滚、升级幂等性、删除后保留记录、月份边界、管理员权限与旧数据提示。验证不查询真实账号或执行数据恢复。

部署后由管理员核对一位已知历史使用量的账号：管理后台与团队后台的累计已用/剩余应一致；历史提交仍在；新帖只消耗剩余额度。如历史追加曾被覆盖，先确认缺失数额再手动补加。
